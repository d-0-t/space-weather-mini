# 07: Inline glossary popups instead of navigating to Explainers

**What to build:** reading flow breaks today — every glossary term is a link that navigates away to the Explainers page anchor, losing the reader's place mid-read (human report, ticket 01 Part D). Terms open their glossary entry inline in a popup instead; the Explainers page remains the full glossary but is no longer a navigation target.

**Background:** the term component (used across the six forecast product pages and the Home live banner — about twenty call sites) takes a term id and renders a link to the Explainers anchor today. The reuse target already exists: the `HelpPopover` component with its `HelpPopoverContent` shape (`label` + `rows`/`text`/`paragraphs` + `footnote`) — the same info-button popup cards on the solar-wind, magnetosphere, live-panel, oval-glow and view-distance surfaces, with the house discipline already solved inside it (summary-triggered details, Escape/outside-click/trigger/X dismissal, focus returned to trigger, viewport clamping). This ticket repoints terms at that component: `GlossaryTerm` keeps its props (term id + visible label, still a real focusable control with visible focus) but opens the entry through `HelpPopover` instead of a router `Link`. Entry content comes from the same glossary entry source the Explainers page already renders — no rewording of entries here, presentation change only. The Part B honesty bounds are unaffected (copy unchanged).

Done 2026-09-13 (TDD, confirmed seams). The glossary source was extracted from `explainers.tsx` into `src/components/explainers/glossary.ts` (`GLOSSARY_ENTRIES` + `getGlossaryEntry`); the Explainers page and the new popups both render that one source, so a definition is never forked. `GlossaryTerm` keeps its props (`termId` + visible label) but renders a real `<button>` (phrasing content, valid inline in the ~20 prose paragraphs and the LiveBanner `<h2>`) that opens `HelpPopover` with the entry body and a footnote link to `/explainers#<id>` ("Read the full glossary"). The trigger is the visible term; an unknown id degrades to plain text rather than a dead control.

Design decisions as built: `HelpPopover` was refactored (user-approved) from `<details>/<summary>` to a `<span>` root + real `<button>` trigger + a body portalled to `#main-content` and placed with fixed viewport coordinates (`placePopover`, pure and unit-pinned). The reason is structural: `<details>` is flow content, invalid inside the prose `<p>`s and the heading, and React's `validateDOMNesting` warns; a button is phrasing content. The portal target is the `main` landmark (not `body`) so the body stays inside a landmark and axe's `region` rule passes. The shared body chrome now lives once in `HelpPopover.scss` as `.help-popover` (each family supplies only its width/paragraph deltas — this also pairs `--font-size-small` with `--line-height-small`); the `summary` prop was renamed `trigger` because no `<summary>` remains. Dismissal returns focus to the trigger on Escape, the X **and** an outside primary click; opening moves focus into the body's first focusable control (the close X), and Tab/Shift+Tab cycle within the body until it is dismissed, so the close button and the full-glossary link are keyboard-reachable and focus never escapes (ticket bullet 1). Reduced-motion is satisfied trivially — no animation was added.
